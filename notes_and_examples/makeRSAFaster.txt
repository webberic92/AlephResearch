You're right to expect RSA accumulators to reduce communication complexity — but the performance drop you’re seeing is not unusual at all in early-stage implementations. Let’s walk through why.

🚨 Why is RSA so much slower right now?
1. RSA Accumulator operations are slow in software

    modpow, BigInt arithmetic, and hash_to_prime() are CPU-bound and costly, especially in Rust with software bigint libs like num-bigint.

    Merkle trees use fast Sha256 + vector ops — very efficient for short txs.

    Note: In your RSA output, CPU usage was lower than the Merkle case — which likely means it was waiting (idle) a lot, possibly due to retries, delays, or poor parallelism.

2. Proof generation and verification is expensive

    For each shard, you do hash_to_prime() and a modpow() — both are expensive.

    You’re verifying 4 proofs per transaction × 25 tx × 25 rounds = 2500 modpows per node.

3. Retries and network delays hurt throughput

    You added retries (good!) — but if nodes are slow to respond or verify, retries introduce delays and slow quorum.

    Each verify_proof is a blocking CPU op, and your code does it serially, so that adds up.

4. No batching or pipelining

    RSA accumulator systems often use batch proving or batch verification to amortize cost.

    If you’re not doing this, the per-shard cost dominates.

5. Possibly suboptimal implementation of hash_to_prime

    Your hash_to_prime is using a simple brute-force prime search, which is correct but very slow.

    A better approach uses a precomputed safe-prime group or specialized fast prime-hashing techniques.

✅ Why Merkle is still faster right now

Merkle tree operations:

    Are linear time and optimized (vector + sha256)

    Use very little memory

    Do not require big integer math

    Don't retry as much (your retries may have only been added for RSA version)
