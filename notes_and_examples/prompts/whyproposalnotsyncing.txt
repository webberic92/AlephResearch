Steps in the Consensus Flow:

    Proposal Phase:
        Node 1 sends its proposal (containing data shards and Merkle proofs) to all other nodes.
        Nodes validate the proposal by checking the Merkle root and reconstructing the unit.

    Prevote Phase:
        After successfully validating Node 1's proposal, all nodes send prevotes for Node 1’s proposal.
        A quorum (e.g., ⌈N+12⌉⌈2N+1​⌉, where NN is the total number of nodes) must be reached before moving to the next phase.

    Commit Phase:
        After reaching quorum in the prevote phase, nodes send commits for Node 1’s proposal.
        If quorum is reached in the commit phase, the proposal is finalized.

    Handling Node 2's Proposal:
        Node 2’s proposal should ideally follow Node 1’s proposal in this sequence, starting with the proposal phase.

Common Issues in this Setup:
1. Proposal Prioritization:

    Problem: Nodes process proposals from Node 2 before completing Node 1's prevote and commit phases.

    Root Cause:
        Lack of prioritization in handling proposals.
        Proposals may be processed in the order they are received rather than the order they were initiated.

    Solution:
        Use a proposal tracker that ensures proposals are processed in the order of their epochs or round IDs.

2. Quorum Calculation Errors:

    Problem: Node 1's proposal doesn’t reach quorum in the prevote or commit phase before Node 2's proposal begins.

    Root Cause:
        Incorrect quorum thresholds may cause nodes to move prematurely to the next proposal.
        Nodes may send prevotes or commits for multiple proposals simultaneously.

    Solution:
        Enforce strict quorum logic where a node only participates in prevotes and commits for a single proposal at a time.

3. Asynchronous Communication:

    Problem: Network delays cause Node 1’s proposal to propagate slower than Node 2’s proposal.

    Root Cause:
        Nodes may start processing Node 2’s proposal before receiving all the messages for Node 1’s proposal.

    Solution:
        Introduce a delay or timeout to wait for messages from all nodes before transitioning to the next phase.

4. Epoch or Round Mismatch:

    Problem: Nodes may treat proposals from Node 1 and Node 2 as being in the same round or epoch.

    Root Cause:
        Incorrect synchronization of epoch or round IDs between nodes.

    Solution:
        Ensure that epoch synchronization logic is robust.
        Use the /sync_epoch endpoint or a similar mechanism to align all nodes on the current epoch or round.

5. Invalid Proposal Validation:

    Problem: Node 1's proposal fails validation on some nodes, leading to delays in reaching quorum.

    Root Cause:
        Incorrect or missing shards, Merkle proofs, or root mismatches.

    Solution:
        Implement detailed logging for the proposal validation process.
        Ensure proposals are correctly constructed and validated at all nodes.

Diagnostic Steps:

    Log Analysis:
        Check the logs of all nodes to verify:
            When Node 1’s proposal reached each phase (prevote, commit).
            When Node 2’s proposal started being processed.
        Look for errors or delays in the prevote and commit phases for Node 1’s proposal.

    Proposal Tracker:
        Ensure the proposal tracker contains entries for Node 1’s proposal before Node 2’s proposal.
        Verify that proposals are processed in the correct order.

    Quorum Check:
        Validate that quorum is correctly calculated for the prevote and commit phases.
        Ensure that nodes only process one proposal at a time.

    Epoch Synchronization:
        Confirm that all nodes are synchronized on the same epoch or round ID.
